# Goal：支持 Git 安装 EAC-skin-loader，并自动补齐皮肤

> 创建日期：2026 年 10 月 4 日。
> 本文是交接给目标仓库 goal 模式的执行计划，不代表任务已经启动或功能已经实现。
> 本文保存在 EAC-Pack 仓库中，但实施目标是 EAC-skin-loader 仓库，不应在 EAC-Pack 中实施代码改动。

## 一、目标与执行原则

在 `DSH-EAC/EAC-skin-loader` 中实现以下用户流程：

```text
Desktop 添加 github:DSH-EAC/EAC-skin-loader
→ 加载器成功安装并启动
→ 自动检查、下载和安装缺失的皮肤
→ 新皮肤登记到现有控制台
→ 保持当前皮肤和用户已有启用状态不变
```

请以此为目标推进诊断、实现、测试和交付，而不是只提交设计文档。

执行约束：

- 仅修改 EAC-skin-loader 仓库；**不要在 EAC-Pack 仓库中实施本任务**。
- 先确认当前 checkout、分支、未提交修改及仓库内 `AGENTS.md`。
- 若没有目标 checkout，先准备合适的工作目录，并遵守环境权限要求。
- 不主动使用 sub-agent；只有获得明确授权后才能委派。
- 优先复用宿主 `pluginManager`、Node.js 内置能力和现有 adapter，不自行执行 `pnpm add` 修改用户 profile。
- 不新增第三方库或外部服务，除非说明必要性并获得许可。
- 推送、发布 Release、覆盖远端资产和修改真实用户 profile，必须先获得明确许可。
- 禁止通过关闭兼容检查、降低测试标准或绕过构建审批来取得表面成功。

## 三、首版范围

### 必须实现

1. **有效的 Git 安装入口**
   - 默认仓库安装不能再落到没有 `dsh.bundle` 的开发清单。
   - 安装后的加载器必须包含已构建的 host/client 入口。
   - 不依赖用户手动执行构建命令。
   - 不把 `prepare/postinstall` 是否执行作为唯一保障。

2. **固定版本的皮肤制品清单**
   - 根据仓库实际包结构确认十三款皮肤，不手工猜测名称。
   - 清单至少记录包名、版本、下载地址、SHA256、字节数和宿主兼容范围。
   - 清单必须由实际构建产物生成并验证，不得使用零 hash 或占位资产。
   - 首版锁定一个经过验证的发布集合，不运行时追踪“最新版”。

3. **一次性自动补齐**
   - 加载器启动后，后台检查并安装缺失皮肤。
   - 下载和安装不能阻塞加载器界面启动。
   - 已有皮肤不自动升级、降级、重装或重新启用。
   - 安装失败的项可重试；成功项不重复安装。

4. **最小状态界面**
   - 显示检查、下载、安装、完成和失败状态。
   - 提供失败重试及自动补齐开关。
   - 区分“加载器可用”和“皮肤集合已补齐”。

### 明确不做

- 完整插件市场、任意第三方插件安装。
- 多套餐、复杂渠道管理和自动升级。
- 自动切换当前皮肤。
- 自动卸载、清理旧皮肤或历史残留。
- 改写现有皮肤视觉实现。
- 重构现有皮肤互斥状态机。
- 复制 EAC-Pack 的全部更新中心和兼容清理逻辑。

## 四、实施步骤

### 阶段 1：冻结分发和安装契约

先检查：

- 宿主如何解析 Git 包、bundle patch、依赖包及 client 模块。
- 根目录分发入口如何保持 `@dsh-eac/ui-skin-loader` 的身份一致。
- `pluginManager` 的安装、启用、状态查询及 reload 行为。
- 十三款皮肤是否存在第三方依赖和额外资产。
- 官方 Desktop 的实际 Node.js 版本是否满足包声明。

优先评估：**独立命名的根目录组合包，依赖固定的加载器制品，并通过 patch 挂载真实加载器。**这样可以保留开发 workspace，避免根目录与子包重名。

必须通过隔离安装验证该结构，不能仅凭路径推断可行。

如果该结构无法满足默认 Git 地址：

- 明确报告原因及证据。
- 提出构建产物分发方案。
- **不要默默把验收地址改成带 `#install` 的分支地址**；这属于用户流程变更，需要确认。

输出简短设计说明：包身份、入口路径、制品来源、安装接口和状态存储位置。确认关键契约后再展开实现。

### 阶段 2：实现 host 侧补齐器

在 host/adapter 边界新增安装能力，保持现有皮肤运行时公共接口不变。

职责：

- 查询实际已安装和启用状态。
- 校验清单及制品。
- 下载到加载器自己的数据目录，不写入 pnpm 管理的包目录。
- 串行调用宿主 `pluginManager` 安装，避免 profile 修改竞争。
- 验证安装结果后才标记成功。
- 为新安装皮肤启用插件，使其完成登记；**不调用皮肤切换操作**。
- 持久化任务状态，能够在 reload 或重启后重新核对现场并恢复。

安全要求：

- 限制下载来源和文件名，防止路径穿越。
- 校验实际字节数和 SHA256；缺少必要校验信息直接拒绝。
- 使用临时文件，验证成功后再原子落入缓存。
- 有超时、有限重试和重复任务防护。
- 网络失败不能导致加载器启动失败。
- 遇到构建审批或兼容错误时显示真实原因，不自动绕过。

### 阶段 3：实现补齐策略与控制台

为首次初始化保存持久状态。

必须区分：

- 待安装、安装中、安装成功、安装失败。
- 已存在且保留。
- 用户关闭自动补齐或明确排除。

特别处理：

- 用户在补齐完成后卸载某个皮肤，不能每次启动又安装回来。
- 已安装但被用户禁用的皮肤保持禁用。
- 已有不同版本的皮肤不自动覆盖，显示版本差异。
- 多窗口、多次点击或 reload 不产生重复安装任务。
- 用户当前 `activeSkin` 不因补齐改变。
- 安装状态与皮肤激活状态分开存储和展示。

先提供最小界面，不重做控制台布局。

### 阶段 4：构建与发布管线

补齐 CI 和产物检查：

- 构建加载器及全部目标皮肤。
- 打包并生成实际制品清单。
- 检查声明、入口、patch、资源、许可证及第三方署名齐全。
- 检查清单引用的每个资产实际存在且校验信息一致。
- 建立加载器版本与皮肤发布集合的明确对应关系。
- 更新 README，说明 Git 安装、首次联网补齐、失败重试及离线能力边界。

发布应分为：

1. 本地实现、验证和候选产物准备。
2. 获得许可后发布、推送并验证公共安装链路。

未发布前，不得声称公共 Git 地址已经修复。

## 五、验收矩阵

| 场景 | 必须满足 |
|---|---|
| 干净 profile Git 安装 | 包可识别，host/client 和控制台可用 |
| 首次补齐 | 目标皮肤安装并登记，当前界面不被切换 |
| 已安装部分皮肤 | 仅安装缺失项 |
| 已有禁用皮肤 | 保持禁用 |
| 已有不同版本 | 不覆盖，显示差异 |
| 首次启动断网 | 加载器仍可用，缺失项可重试 |
| 下载中断、hash/大小错误 | 不安装损坏资产，不标记成功 |
| 宿主安装失败或需要审批 | 报告真实状态，不绕过、不无限重试 |
| reload、重启、多窗口 | 不重复安装，不丢失进度判断 |
| 用户主动卸载 | 不在每次启动强制补回 |
| 关闭自动补齐 | 不发起新的自动补齐任务 |
| 皮肤回归 | 切换、还原默认、持久化和故障隔离仍正确 |

执行仓库既有 test、lint、typecheck 和 build，并补充自动测试。

**类型检查和 mock 测试不能代替 Desktop 验收。**最终应在目标官方 Desktop 上验证主路径；若环境不具备，明确列出未验证项。
